## How to read this table

| Column | Meaning |
|---|---|
| **Boundary ID** | Short code used by the adversary console to name each refusal point. |
| **File / Function** | Where the check lives in the source tree. |
| **Refusal mechanism** | What actually stops the caller: a Solidity custom error, an HTTP 4xx, a thrown JS error, or a structural absence (the call never reaches the gated code). |
| **Trust boundary** | Where in the stack the check sits. |
| **Reachable from untrusted input?** | Can a caller who controls the request reach this check without cooperation from the server? |
| **Test coverage** | Which test file(s) exercise this boundary. Empty means no test covers it. |

## Notes on the trust model

1. **The contract is the outer authority**: Solidity custom errors in `ProcurementEscrow` are the hardest boundary in the system. They cannot be bypassed by any server-side bug because they execute in the EVM, not in Node.js.

2. **Server checks are the soft boundary**: The role token, the `assertMayProceed` gate, and the HMAC verification are server-enforced. They are correct as written, but they live in mutable JavaScript and can be weakened by a future change. The adversary suite exists to catch that regression.

3. **Client checks are informational only**: The interface dims controls and hides actions for roles that don't hold them. These are UX conveniences; every corresponding server-side check has been verified in `roles.test.js`.

4. **Structural absences**: Several boundaries work by the code literally not having the imports or the read path to take a dangerous action (see `counsel.js`, `documents.js`). These are the most robust kind of boundary and the adversary suite verifies them statically (attack D2).

5. **The phrasing layer (summary.js)**: The LLM is downstream of the arithmetic. Numbers flow in as finished text; the model is a copy-editor. The invented-figure check is the line that enforces this claim and is the one boundary not covered by an existing test — attack C2 covers it.
