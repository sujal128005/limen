Limen · Supporting documentHow to check it
Start here

Four commands, and you do not have to believe us.

Everything below runs offline. No API key, no wallet, no network: the chain is a real EVM inside the process, and the payment rail falls back to a local implementation that runs the same code path including its webhook.

Run it

# Node 20 or newer
npm install
npm start          # builds the frontend, boots the chain, serves on :4000

Boot compiles three Solidity contracts, deploys them, registers fifteen suppliers on chain and funds the buyer: about 3.6 seconds, peaking near 290MB.

Check the claims

npm test           # 205 unit tests, including 36 on roles and signatures
npm run sweep      # 139 checks against the running HTTP surface

The claim most worth checking by hand

The deck says a person holding a terminal cannot bypass the approval. This is the exact sequence that used to work, and what it does now. 

# no credential at all
curl -XPOST localhost:4000/api/deal
400 {"error":"Sign in to continue. This action is restricted to a role."}

# signed in as sales, at a purchase awaiting payment
curl -XPOST localhost:4000/api/purchase/release -H "authorization: Bearer $SALES"
400 {"error":"Sales / Procurement cannot do this.
     Finance / Payments holds this permission."}
Why this document exists An earlier version of this system had an approval checkpoint that lived only in the browser. Three curl requests with no signature funded the escrow and released the money. The checks above are the receipts.

Limen · Supporting documentArchitecture
Architecture

Four layers, and only one of them can authorise a payment.

The layers are ordered by how much they are trusted, and each one can only be reached through the one above it. A layer cannot widen its own authority, because the authority is held by the layer beneath.

LayerResponsibilityCannot
Language model Rewrites explanations into plain English Introduce a number, name or claim. Sign, spend, or judge whether a person approved
Deterministic engine Parsing, screening, bargaining, ranking. Every figure the product shows Move funds or write a policy
Authorisation Workflow state, role permissions, the fingerprint an approval binds to Reach a signer or a network. The module has no imports
Smart contract The spending ceiling, escrow custody, settlement, supplier reputation Be edited by anything running above it

The capability boundary is an import list

Two modules decide what the system will say about a run: the reasoning responder and the decision brief builder. Both have zero imports. They receive a frozen projection of the run and return text. There is no contract handle, no signer, no database and no network call available to them, so no output they produce can move anything.

Why this rather than a prompt instruction A prompt is a request. An import list is a fact about the program. A module that was never handed a signer has nothing to argue about.

Two identities, deliberately separate

  • The buyer holds the funds and publishes the policy, stored against the buyer's own address.
  • The agent holds a separate key, nominated by that policy. It can create deals under the ceiling and nothing else.
  • The contract reads policies[buyer]; setAgentPolicy writes to policies[msg.sender]. An agent writing itself a larger mandate writes it where the check never looks.

The workflow

Twelve states, derived rather than stored.

The state of a purchase is computed from the facts recorded about it, never written down as a field. That removes the possibility of the stored state and the actual state disagreeing, which is the usual way a workflow gets bypassed: something writes APPROVED without an approval ever happening.

What the chain enforces

The spending limit is contract state.

Three contracts compile and deploy at boot. The escrow holds custody and the ceiling, the registry holds supplier reputation, and a test token stands in for a stablecoin. The checks below run inside createDeal, so they apply to any caller by any route.

ExceedsPerDealCapA single purchase is above the buyer's per-deal ceiling
ExceedsTotalCapCumulative spend under this policy would exceed its envelope

Limen · Supporting documentAttack demonstrations
Proof, not a promise

Two demonstrations, shipped in the product.

Attack 1: told to overspend, with a real key

A route in the product forwards a purchase above the ceiling without pre-checking the amount, on purpose, so the refusal comes from the EVM rather than from our code. It returns the decoded error and proof that no state changed. 

POST /api/deal/attempt-over-limit
{ "rejected": true, "attempted": 1250, "cap": 1200, "overBy": 50,
  "errorName": "ExceedsPerDealCap", "stateUnchanged": true }
A bug we found writing this document That route took the amount from the caller. An amount under the cap was accepted, which funded escrow with no approval and no role, and recorded nothing the workflow could see. A demonstration route was a funding route with a friendlier name. The attempt is now floored above the ceiling, so the function can only ever produce a revert.

Attack 2: the agent rewrites its own limit

POST /api/attack/raise-own-cap
{ "selfPolicyTxSucceeded": true,     // the agent really did write it
  "buyerCapUnchanged": true,
  "buyerCapAfter": 1200,
  "spendRejected": true }

The escalation transaction succeeds. The spend that follows it still fails, because the contract reads the buyer's policy and the agent wrote its own.

Limen · Supporting documentPayments
Payment architecture

The contract is asked before the rail is touched.

1
Workflow gate
Right state, right role, and the approval still matching the purchase. A stale approval stops here.
2
Contract check, by static call
The release runs against the real EVM without mining a transaction. A revert here ends the request, and the payment provider is never contacted.
3
Payout created
Under a key derived from the workspace, the document reference and the approval fingerprint. A retry after a timeout returns the original payout instead of making a second one.
4
On-chain release
Escrow pays the supplier and the registry records the settlement and the reputation change.
5
The rail reports back
The purchase sits in PAYMENT_PROCESSING until a signed webhook moves it to settled, failed or reversed.
Step 2 is the one that matters A static call executes the function against current chain state and reverts with the same custom error a real call would, without mining anything. There is no path from there to the payment provider if it throws, and a test counts the calls to prove it.

Limen · Supporting documentPayments
Payment lifecycle

A created payout is an instruction, not money in an account.

A product that flips to paid on a 200 from the create call is lying about the one fact it exists to report. A purchase sits in PAYMENT_PROCESSING until the rail says otherwise.

Webhook rules

  • Signature over raw bytes. The request buffer is kept before parsing, because re-serialising a parsed body produces a different string and the check would fail in a way that looks like forgery.
  • Duplicates ignored. Providers retry until they get a 2xx. A repeated event id is recorded and not applied.
  • Order not assumed. A queued notification can overtake the one that followed it, so a non-terminal event arriving after a terminal state is recorded and ignored rather than applied.
  • Unmatched events acknowledged. A 4xx would make the provider retry an event that will never match anything, forever.
  • No model involvement. Payment state is a fact reported by the rail, not a judgement.
Runs without credentials With no provider keys set, payouts run on a local rail that holds the payout in processing and then delivers a real event to the same handler the live provider posts to. The asynchronous path is the path that runs, so a reviewer sees the true lifecycle rather than a boolean.

Limen · Supporting documentTest evidence
Test evidence, part two

The 36 checks that prove separation of duties.

Every one runs over HTTP against the booted server with a real signed token, because a unit test of a guard function proves the function works, not that the route calls it.

A test we removed rather than kept One assertion read !n.agreed || n.finalTotal <= 1200. Neither field exists, so !undefined was true and the check passed without comparing anything to the ceiling. It is now an explicit check on every offer the agent makes.

The token is the only authority

  • An unsigned caller cannot start a run
  • A role claimed in the body is ignored
  • A tampered token is refused
  • A token is only good for its own workspace

Nobody does another's job

  • Sales cannot pay
  • Sales cannot self-approve
  • Sales cannot reach APPROVED by any route it holds
  • The head cannot pay
  • The head cannot run sourcing
  • Finance cannot approve or pay unapproved work

The workflow cannot be jumped

  • SALES_REVIEW cannot become PAYMENT_READY
  • HEAD_APPROVAL cannot become SETTLED
  • A rejected purchase is finished

The approval binds to the deal

  • A changed amount invalidates it
  • A changed supplier invalidates it
  • It reports itself stale before anyone tries to pay

Contract, rail and webhooks

  • A contract refusal means zero calls to the rail
  • The agent cannot escalate the buyer policy
  • The demonstration route cannot fund anything
  • Releasing leaves it processing, not settled
  • A repeat does not create a second payout
  • An unsigned webhook is refused
  • A duplicate event changes nothing

Limitations

What is demo-grade, and what would change it.

These appear on screen in the product as well, not only here. A claim shipped without its boundary is not a claim worth making.

LimitationWhat it meansResolved by
Not yet on a public chainDeployment is a deliberate step that records addresses to a manifest, and the server attaches rather than redeploying, so a testnet run is configuration rather than codeFund a key, run the deploy script once, commit the manifest it writes
Delivery is buyer-attestedThe contract controls when reputation is written, but a buyer and supplier acting together could settle a deal that never shippedOracle or carrier attestation
Suppliers are seededFifteen suppliers shaped like a directory API response, with simulated counterparties holding private floor pricesLive directory adapter, supplier-side agents
Signing keys are not identitiesAn approval can carry a verified EIP-712 signature over the commercial terms; the key behind it is not bound to a verified legal identityIdentity verification at onboarding
Payouts are test modeTest credentials, or a local rail that runs the same path including its webhookProduction credentials and a funded account
Suppliers have no bank detailsA live payout needs a verified fund account per supplier, and one cannot honestly be invented for a demoSupplier onboarding, one record each
One instanceWrites are locked per workspace and version-checked, so a second instance would be correct; running one is a cost choiceNothing. Raise the instance count
The constraint we hold None of the work above may weaken the property the project exists to demonstrate. The deterministic core and the contract layer are not touched by any of it.
